# 安装部署与初始化数据

> 从零把「GitHub 飙升雷达」跑起来，并把数据补上的完整说明。
> 架构、表结构、接口细节见 [`系统设计.md`](系统设计.md)；数据源能力与额度见 [`数据来源与采集详解.md`](数据来源与采集详解.md)。

---

## 1. 环境要求

| 项 | 要求 |
|---|---|
| 系统 | Linux / macOS（Windows 建议 WSL2） |
| Docker | 20.10+ 且带 `docker compose` v2 |
| 内存 | 建议 ≥ 4 GB（`db` 默认 `shared_buffers=1GB`） |
| 磁盘 | 结构 + 配置约 100 MB；导入全量数据后约 5–10 GB |
| 网络 | 能访问 `api.github.com`（配了代理则走代理，见第 8 节） |

```bash
# Debian/Ubuntu 安装 Docker
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER    # 重新登录后免 sudo
```

## 2. 部署四步

```bash
git clone https://github.com/2431520236/githubStar-rank.git
cd githubStar-rank

cp .env.example .env            # ① 准备配置
#   至少改这三项：
#   GH_ADMIN_PASSWORD=换成你自己的密码
#   GH_AUTH_SECRET=随便一串长随机值
#   GH_GITHUB_TOKEN=ghp_xxx    （可选：不填也能跑，但采集会很慢，见第 4 节）

docker compose up -d            # ② 起 db + api
docker compose logs -f db       # ③ 看到「[initdb] 完成：处理 N 个文件」即建库结束
docker compose ps               # ④ 两个容器都 running / healthy 就成了
```

浏览器打开 **`http://127.0.0.1:9951/`**（局域网把 `localhost` 换成这台机器 IP）。
默认管理员 `github / github`，登录后可在页面右上角「改账密」（存库，优先于 `.env`）。

> 初始化只跑一次（写哨兵 `.init_done`），之后再 `up -d` 不会重复导入。

### 改了 `.env` 但行为没变？

`restart` **不重读 `.env`**。改端口 / Token / 账密后必须重建容器：

```bash
docker compose rm -sf api && docker compose up -d api
```

### 改了代码怎么生效？

`server/app`、`server/web`、`server/tools` 都是 bind mount，**不用重建镜像**：

```bash
./restart.sh          # 等价于 docker compose restart api，约 3 秒
```

只有改了 `server/Dockerfile` 或 `server/requirements.txt` 才需要 `docker compose build api`。

## 3. 数据从哪来（关键）

**仓库自带的 `docs/sql/` 只有表结构与配置**（`01-schema.sql` / `10-config.sql` / `25-watch.sql` / `70-pool.sql` / `99-verify.sql` / `MANIFEST.json`）。
仓库主数据（`20-repo-*.sql`）与 star 历史事实层（`30-weekly-*.sql` / `35-daily-*.sql`）体积达数百 MB，**超出 GitHub 单文件 100 MB 上限，不入库**。

所以刚部署完：16 张表结构齐全，但 `gh_repo` 等数据表是空的，页面暂时没有数据。两条路补上：

### 路线 A：自己采集（推荐，最省事）

配好 `GH_GITHUB_TOKEN` 后，在页面「**采集与调度**」里按顺序点：

| 顺序 | 动作 | 说明 |
|---|---|---|
| ① | **补全详情（多线程）** | 从 GitHub 拉仓库详情（star、语言、协议、描述…），勾「只补缺」 |
| ② | **采集 star 历史** | 拉官方 star 事件，写入周/日事实表；每轮约 1000 仓，可反复执行 |
| ③ | **每日快照 / 昨日新增** | 回填 1/7/30 天增量，并冻结榜单快照 |

也可以用接口触发（需管理员登录态 Cookie）：

```bash
curl -XPOST localhost:9951/api/system/jobs/collect_history/run
curl -XPOST localhost:9951/api/system/jobs/rollup/run
curl -XPOST localhost:9951/api/system/jobs/daily_rank/run
```

跑完第一批（约 1000 仓）周榜就有内容，不必等全量。

### 路线 B：导入自己的资料包

在**已有数据的库**上用仓库自带工具导出（自动分片、对源库只读）：

```bash
python3 server/tools/export_sql.py --out docs/sql --chunk-rows 200000
# 产物：01-schema / 10-config / 20-repo-*.sql / 25-watch / 30-weekly-* / 35-daily-* / 70-pool / 99-verify / MANIFEST.json
```

把产出的 `*.sql` 放回 `docs/sql/`，然后 `docker compose down && docker compose up -d`（或删掉卷上的 `.init_done` 哨兵后重启 db）即会自动按文件名顺序导入。

> 也可以手工导入：`for f in $(ls -1 docs/sql/*.sql | sort); do psql ... -f "$f"; done`，详见 [`sql/README.md`](sql/README.md)。

### 校验数据是否真的进去

```bash
docker compose exec -T db psql -U postgres -d github -c "
select (select count(*) from gh_repo) repo,
       (select count(*) from gh_repo_star_weekly) weekly,
       (select count(*) from gh_repo_star_daily) daily,
       (select count(*) from gh_rank_snapshot) snap;"
```

| 结果 | 结论 |
|---|---|
| `repo=0` | 没导入数据也没采集 → 走路线 A 或 B |
| `repo>0, weekly=0` | 有仓库没事实 → 跑「采集 star 历史」 |
| `weekly>0, snap=0` | 缺快照 → 跑「每日快照」（或 `rollup` + `daily_rank`） |
| 图有数据但数值明显不对 | 库里 `gh_stat_period` 是从别处导入的旧统计 → **不要导入这张表**，清掉后重算：<br>`TRUNCATE gh_stat_period, gh_rank_snapshot;` 再跑快照 |

`gh_stat_period`、`gh_rank_snapshot` 是**算出来的派生表**，导出工具默认跳过 —— 导进别人的旧数值比空表更难发现。

## 4. GitHub Token：不填也能跑，但很慢

| 认证方式 | 额度 | 后果 |
|---|---|---|
| 匿名 | 60 次/小时 | 2000 个仓库的 star 历史要跑几十天 |
| 带 Token | 5000 次/小时 | 一天内可跑完一轮 |

申请步骤见 [`GitHub-Token-指南.md`](GitHub-Token-指南.md)，只需勾 `public_repo`（读公开仓库）即可。

## 5. 验收清单（部署后逐条跑）

```bash
# ① 容器 + 端口
docker compose ps
ss -tln | grep 9951                      # 期望 0.0.0.0:9951

# ② 健康检查（code 应为 0）
curl -s localhost:9951/api/system/health

# ③ 页面 200
curl -s -o /dev/null -w '%{http_code}\n' localhost:9951/

# ④ 数据接口（每条之间 sleep 2，否则会撞 1 次/秒限流返回 429）
curl -s 'localhost:9951/api/stats/screen'
curl -s 'localhost:9951/api/ranks?metric=gain&period_type=rolling7&page_size=3'
curl -s 'localhost:9951/api/stats/weekly-trend?year=2026'

# ⑤ 管理员登录
curl -s -c /tmp/c.txt -XPOST localhost:9951/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"<管理员>","password":"<密码>"}'
curl -s -b /tmp/c.txt localhost:9951/api/auth/me      # is_admin:true

# ⑥ 接口冒烟（14 个）
docker compose exec -T api python3 tools/selfcheck.py
```

**浏览器侧**（`curl` 200 不代表页面画出来了）：打开 `/` 看周柱图有柱子、总榜有仓库名、控制台 0 错误；再点开 `/rank.html` 确认「共 N 条」不是 0。

## 6. 备份、恢复与重置

数据库落在 Docker **命名卷**里（容器内 `/var/lib/postgresql/data`），不在容器中，所以 `stop` / `start` / `restart` / `down`（不带 `-v`）都不会丢：

```bash
# 卷在哪（名字 = <compose 项目名>_<compose volumes 里的 key>）
docker volume ls | grep ghradar
docker volume inspect "$(docker volume ls -q | grep ghradar | head -1)"

# 备份
docker compose exec -T db pg_dump -U postgres -d github | gzip > backup_$(date +%F).sql.gz

# 恢复
gunzip -c backup_2026-10-14.sql.gz | docker compose exec -T db psql -U postgres -d github

# 只导出结构
docker compose exec -T db pg_dump -U postgres -d github --schema-only > schema.sql
```

⚠️ **`docker compose down -v` 会删卷 = 删库**（下次启动重新导入，数据全没）。彻底重来才用它。

## 7. 对外发布（反代 / 公网）

| 路径 | 做法 | 适合 |
|---|---|---|
| **A. 内网 IP + 端口** | 直接访问 `http://<内网IP>:9951/` | 自己用 / 团队内网 |
| **B. 反向代理** | 宿主 nginx / caddy 反代 `127.0.0.1:9951`，绑独立域名或独立端口 | 要 HTTPS、要访问控制 |
| **C. 公网穿透** | frp / Cloudflare Tunnel | 没有公网 IP |
| **D. 镜像分发** | `docker save` + 导出数据卷 → 目标机 `load` + `up -d` | 多机 / 离线交付 |

⚠️ **不能用子路径反代**（如 `/githubstar/`）：前端资源全是根绝对路径 `/web/...`、`/api/...`，挂到子路径下会 404。要支持子路径必须同时改前端 base 和后端路由前缀。

nginx 示例：

```nginx
location / {
    proxy_pass http://127.0.0.1:9951;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

**对外暴露前必须做**：改掉默认管理员账密、`GH_AUTH_SECRET` 设随机值、确认反代层有访问控制。

## 8. 代理

代理是可选项，**默认留空**。留空时跟随运行环境的系统 / 环境变量（`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY`），都没有则直连。

优先级：**显式 `GH_PROXY` > 系统 / 环境变量 > 直连**。

```bash
# .env 里显式指定（会同时用于 GitHub 采集与模型请求）
GH_PROXY=http://127.0.0.1:7890
```

改了 `.env` 记得重建容器（`restart` 不重读 `.env`）。

## 9. 同机再起一套实例

用于验证部署流程、试新数据包，不影响原有那套：

```bash
./scripts/deploy-instance.sh                        # 起一套（端口 +1）
./scripts/deploy-instance.sh --port 9953            # 再起一套 9953
./scripts/deploy-instance.sh --sql /path/sql-full   # 指定数据包
./scripts/deploy-instance.sh --down --port 9952     # 删掉这套（容器 + 卷 + 目录）
```

四条隔离线：**目录、compose 项目名（`-p`）、容器名、数据卷**，端口一律 +1。

⚠️ 不要在已有实例目录里裸跑 `docker compose up -d` —— 会按目录名落到默认 compose 项目名，可能顶掉已有容器和端口映射。

⚠️ 两套如果填**同一个 GitHub 账号的 Token**，5000 次/小时是**账号级共享**的，都开自动采集会互相抢额度，症状是两边都出现 `403 API rate limit exceeded`。要么让第二套只做展示（关掉它的调度：`UPDATE gh_app_setting SET value='false'::jsonb WHERE key='scheduler.enabled';`），要么换独立账号的 Token。

## 10. 排错

| 症状 | 处理 |
|---|---|
| 页面打开但全是空 | 库没数据 → 见第 3 节；先查 `gh_repo` 行数 |
| 榜单页显示「尚无快照」 | 跑一次「每日快照」（或 `rollup` + `daily_rank`） |
| 采集全部失败 | 没配 Token（匿名 60 次/小时）；`curl localhost:9951/api/system/rate-limit` 看剩余额度 |
| 接口 429 | 内置 1 次/秒 + 20 次/秒限流，连续 curl 记得 `sleep 2` |
| 配置改了但行为没变 | `restart` 不重读 `.env`，要 `rm -sf api && up -d api` |
| 局域网访问不了 | 确认监听 `0.0.0.0`（`ss -tln \| grep 9951`），再查宿主机防火墙 |
| 本地 curl 502 / 超时 | 运行环境里设了 `all_proxy` 时，本机访问本机服务要加 `--noproxy '*'` |
| 容器起不来 | `docker compose logs db` / `docker compose logs api` 看具体报错 |
| 想彻底重来 | `docker compose down -v && docker compose up -d`（**会删数据**） |

## 11. 常用命令

| 操作 | 命令 |
|---|---|
| 重启 API（约 3 秒） | `./restart.sh` |
| 重启数据库 | `docker compose restart db` |
| 看日志 | `docker compose logs -f api` / `-f db` |
| 进数据库 | `docker compose exec db psql -U postgres -d github` |
| 进容器 | `docker compose exec api sh` |
| 资源占用 | `docker stats` |
| 接口冒烟 | `docker compose exec -T api python3 tools/selfcheck.py` |
