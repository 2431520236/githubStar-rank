## 二、标准：两套采集路径（逐条对照代码）

### A. 主动拉取（人工执行 `server/tools/*.py`）

| 脚本 | 候选标准 | 单次规模 | 写入方式 |
|---|---|---|---|
| `rebuild_star_history.py` | `stars 倒序前 --pool-stars(默认2000)` **∪** `GREATEST(star_gain_7d, star_gain_30d) 倒序前 --pool-gain(默认500)`，按 `id` 并集去重 | 逐仓 1 页 = 最新 30 周；`--concurrency 12` | `--truncate` 先 `TRUNCATE` 两表；`ON CONFLICT (repo_id, week_start) DO UPDATE` |
| `backfill_pool.py` | 读名单文件 `server/data/todo_names.tsv`（22,773 行，来自 ClickHouse 逐周 top2000 并集），只取 `history_synced_at IS NULL` | 分块 `CHUNK=200`，跨额度窗口续跑，12 并发 | 同上 upsert |
| `POST /api/history/collect` | 走下方 `candidates_for_history` | 由请求参数给 limit | 同上 |
| `tools/_legacy_ch/*`（已废弃） | ClickHouse playground `github_events` | — | **禁止再用**（第二套源混写同一张表） |

### B. 定时任务（`app/services/scheduler.py` 的 `_build_tasks()`）

| 任务 | 触发 | 标准 |
|---|---|---|
| `collect_history` | tick 60s → `_every(3600)` + 内部「距上次 >1 天」 | `candidates_for_history(limit=1000, refresh_after_days=1, only_missing=True)`，`concurrency=3` |
| `collect_detail` | 每 86400s | 补 `detail_synced_at IS NULL` 的 20 个仓 |
| `rollup` | 每 86400s | `facts_service.rollup_gains()` 重算 `star_gain_1d/7d/30d/60d` |
| `daily_rank` | 每天 `WEEKLY_RANK_AT` | 日/周/月 × gain/total 六组快照 |
| `weekly_rank` | 每周一 | 最近 12 周 gain 榜 + 本周/本月 total/gain |
| `watch_check` | 每 600s | 关注提醒 |
| `backfill` | 每 86400s | `backfill_service.run_round()` |
| 已删除 | — | `daily_snapshot`（假日增 8796 万）、`daily_ch_increment`（ClickHouse 混写）、`ai_summary` / `ai_month_top` |

`candidates_for_history()` 的 SQL（**唯一候选标准**）：

```sql
SELECT id, full_name, stars, star_gain_7d FROM gh_repo
WHERE history_synced_at IS NULL OR history_synced_at < now() - make_interval(days => 1)
ORDER BY star_gain_7d DESC NULLS LAST, stars DESC LIMIT 1000
```

**⚠️ 标准缺陷（覆盖率上不去的机制性原因）**：排序键 `star_gain_7d` 本身就由 `rollup` 从「已有周历史」算出。
没历史的仓 `star_gain_7d = 0/NULL` 永远排在末尾 → 每天被采的永远是已经采过的那 1000 个头部仓，
新仓/长尾仓**永远轮不到**。721,562 仓按此速率（1000/天）轮一遍需约 2 年，实际永远只覆盖头部。

## 三、「一周 114 万」定性

**数值出处**：`2026-10-05` 那一周 `SUM(weekly_new) = 1,147,282`；日表同周聚合 `SUM(delta_stars) = 1,143,886`（两表自洽差 3,396，来自 `days` 缺天）。

**关键事实 1：114 万不是孤立异常，近 20 周每周都在 95~115 万。**

**关键事实 2：它不是重复。** DB 唯一约束 `(repo_id, week_start)` 在，同仓同周只可能一行；`source` 只有一种。

**关键事实 3：它不是假增量。** 全表 `weekly_new > 仓库总 star` 的只有 16 行 / 11 仓（列表为真实爆仓，如 `deepseek-ai/deepseek-harness` 238,122 star 里 08-10 那周 +138,715）。

**关键事实 4：用官方接口独立回拉 11 个仓（11 次请求），库内值与官方逐周一致。** 抽样：

| 仓 | 周 | 官方 api | 库内 db |
|---|---|---|---|
| `morluto/rea` | 2026-10-05 | 116,277 | 116,578 |
| `deepseek-ai/deepseek-harness` | 2026-08-10 | 138,689 | 138,715 |
| `NousResearch/hermes-agent` | 2026-10-05 | 2,089 | 2,080 |
| `mattpocock/skills` | 2026-10-05 | 10,916 | 10,842 |

差异形态固定为两类，都不是错数据：
1. **「补采时刻 vs 现在」的自然差**：10-12 采集时那一周尚有几天没走完 → 库内比现在略少（`morluto/rea` 10-12 那周：库内 6,880 vs 现在 90,204，因本周还在长）。
2. **ISO 周一重聚合的边界归属差**：官方按周日切周、项目按周一重聚合，天落边界时会产生 ±几~几十 的归属差。

**关键事实 5：114 万里约 28.8% 来自「`stars=0` 未回填详情」的仓**（7,683 仓合计 8,969,249 / 全表 31,129,727）。

### 结论

> 114 万 = **9,443 个头部仓在那一周的真实新增 star 合计**（官方逐日明细求和），
> 不是重复、不是假增量。但它**不能当作「全站一周新增」读**：它只覆盖 9,443 个仓，
> 且周与周之间**不可比** —— 覆盖仓数从 3 月的 4,606 一路涨到 10 月的 9,514（因为 30 周滚动窗口
> 每重拉一次就多覆盖一批仓），周值上升里混着「覆盖面增长」而非纯「star 增长」。

## 四、重复 / 业务唯一性

### DB 层：健全，无重复
- `uq_gh_star_weekly (repo_id, week_start)`、`uq_gh_star_daily (repo_id, stat_date)` 均在，写入全部走 `ON CONFLICT DO UPDATE`。
- `gh_repo.full_name` 有唯一约束；忽略大小写查重：**0 组重复**。

### 业务层：有重复 —— 改名仓各持一份相同历史（**唯一性口径缺口**）

指纹 = 逐周 `(week_start, weekly_new)` 序列的 md5，判据 `≥5 周 且 sum≥500`：

| 指标 | 值 |
|---|---|
| 重复组 | **51 组** |
| 涉及仓 | **105 个** |
| 虚增周新增合计 | **1,001,882**（占周表总量 31,129,727 的 **3.2%**） |

实例（每组两个名字，逐周数值逐位相同）：

| 保留仓（stars>0） | 重复仓（stars=0） | 每组周增 |
|---|---|---|
| `affaan-m/ECC` (268,567) | `affaan-m/everything-claude-code` | 185,871 |
| `mauriceboe/TREK` | `mauriceboe/NOMAD` | 14,700 |
| `getagentseal/codeburn` (11,265) | `AgentSeal/codeburn` | 11,396 |
| `chuspeeism/dashi-ppt-skill` (8,911) | `chuspeeism/dashiAI-ppt-skill` | 9,409 |

**根因**：业务唯一键定义错了。事实表主键是 `(repo_id, week_start)`，而 `repo_id` 是**本地自增序列**
（`gh_repo.id`，非 GitHub repo id）。仓改名后官方 `stargazers/history` 按**新名**返回完整历史，
而 `gh_repo` 里旧名行仍在 → 新名插入新 `repo_id` → 同一仓库被写第二份历史 → 榜单单仓被算两遍。

**正确口径**：一个 GitHub 仓库的业务唯一性 = **GitHub repo id（或 node_id）**，不是 `full_name`、更不是本地自增 id。
`gh_repo` 目前**没有保存 GitHub repo id 字段**（表结构已核，只有 `id/full_name/html_url` 等），这是必须补的。

## 五、其余问题清单（按严重度）

| # | 问题 | 实测证据 | 影响 |
|---|---|---|---|
| 1 | **覆盖率 7.8%** | 52,252 个统一口径仓中 4,084 有周历史 | 「每周 star」图表/榜单只代表头部；长尾完全缺席 |
| 2 | **改名仓重复** | 105 仓 / 虚增 1,001,882 | 单仓榜、周汇总虚高 3.2% |
| 3 | **日表 `stars` 列 99.99% 为 0** | 1,255,674 行中仅 118 行 `stars>0` | 「当日累计 star」口径失效；任何用该列算累计/差值的下游不可靠（10-13 已加 `_validate_days` 拦截，但**历史脏行未清、未回填**） |
| 4 | **`gh_stat_period` 周汇总 W30 起 13 周全为 0** | W12~W29 有值（非零 18 条），W30~W42 全 0 | 前端降级源读出 0；日粒度 20 条 `gain_sum` 亦全 0 |
| 5 | **`days` 数组 46% 不足 7 天** | 108,190 / 233,922 行 | 设计所致（`github_client` 中 `if n:` 跳过 `count=0` 的天），不损失 `weekly_new`；但会让「按天展开」的 `star_gain_1d/7d` 在小样本仓上偏低 |
| 6 | **本周（W42/10-12 之后）无数据** | 日表 max=10-12，库内 W42 仅 1,974 行 | 大屏「今日新增」类指标为 0 |
| 7 | **候选排序马太效应** | `ORDER BY star_gain_7d DESC` | 新仓/长尾永不被采集（见第二节） |

## 六、修复方案（按优先级）

1. **补 GitHub repo id（业务唯一键）** —— `gh_repo` 加 `github_id bigint` + 唯一索引；采集详情时落值。
   改名检测：同一 `github_id` 出现多个 `full_name` 行 → 合并为一行（保留 `stars>0` 者，`UPDATE ... SET repo_id` 迁移事实行，再删重复仓），最后重跑 `rollup_gains()`。
   *立即止血*：现有 51 组 / 105 仓可先按指纹法清（保留 `stars>0` 优先、否则 `id` 最小）。
2. **打破候选马太效应** —— `candidates_for_history` 增加「从未采集」优先档：
   `ORDER BY (history_synced_at IS NOT NULL), star_gain_7d DESC NULLS LAST, stars DESC`，
   或给 `history_synced_at IS NULL` 的仓独立配额（如每次 50% 名额）。
3. **清日表 `stars=0` 脏行并回填** —— 10-12 那批日行的 `stars` 由 10-13 新增的 `_to_weeks` 倒推逻辑已能算真值；
   重跑一次 `collect_history`（带 `ids`）即可覆盖回填，`ON CONFLICT DO UPDATE` 幂等。
4. **重建 `gh_stat_period`** —— `W30~W42` 的 `gain_sum` 从周表重算（`SUM(weekly_new) GROUP BY week_start`），
   并统一口径（当前 `note` 里 `metric=total/gain` 混杂、`frozen` 状态不一致）。
5. **明确「一周新增」的对外口径** —— 建议接口/前端标注为
   「**覆盖 N 个仓的周新增合计**」，并在柱图上给出覆盖仓数（`count(*)`），避免被读成全站量级。
6. **补 W42 之后** —— 定时 `collect_history` 恢复每日跑（当前 `_collect_history` 判断「>1 天」即可），
   或手动 `POST /api/history/collect`。
