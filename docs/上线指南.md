## 2. 四条上线路径对比

| 路径 | 做法 | 前置条件 | 优点 | 缺点 |
|---|---|---|---|---|
| **A. 内网 IP + 端口**（现状） | 直接访问 `http://<内网IP>:9952/` | 无 | 零成本，已完成，已可用 | 只有内网可达；IP 变了地址就变 |
| **B. 反向代理（独立端口 / 子域名）** | 宿主 nginx/caddy 反代 `127.0.0.1:9952`，绑 `gh.xxx.com` 或 `:8080` | 宿主需有反代服务 + 端口；子域名需 DNS | 可挂 HTTPS、可做访问控制、地址稳定 | ⚠️ **必须独立域名或独立端口，不能子路径**（前端 `/web/*` 绝对路径）；当前宿主 **80/443 无监听**，唯一的 nginx 进程在别的容器里（不是可用的宿主反代），需新起 |
| **C. 公网穿透** | frp / Cloudflare Tunnel 把 9952 暴露出去 | 有公网服务器或 CF 账号 | 外网可访问、免公网 IP | 暴露面变大：必须先把管理员账密从默认 `github/github` 改掉、`GH_AUTH_SECRET` 设随机值；公网扫描会打 `/api/*`（已有 1 次/秒 + 20 次/秒限流，但建议再加反代层鉴权） |
| **D. 镜像分发到其他机器** | `docker save ghradar-api:9952` + 导出数据卷 → 目标机 `load` + `up -d` | 目标机有 Docker；数据要另带（卷不会跟着镜像走） | 多机部署 / 离线交付 | 数据（PG 卷）才是主体，镜像只有 175MB；换机等于「重装一套」，见 README「空库部署」五步 |

**为什么不支持子路径反代（关键约束）**：`index.html` 里是 `href="/web/css/app.css"`、`src="/web/js/screen.js"` 这类**根绝对路径**，所有 `api.get('/api/...')` 也是绝对路径。挂到 `http://host:8080/githubstar/` 下，浏览器会去请求 `http://host:8080/web/...` → 404。要支持子路径必须改前端 base + 后端路由前缀，属于改造项，不建议为上线去做。

## 3. 推荐发布流程（以后每次更新代码都照这个走）

### 3.1 标准发布（只改代码，最常见）

```bash
cd githubstar-9952

# 0) 备份（代码 + 关键文档，约 1MB）
BK=backups/code-$(date +%Y%m%d_%H%M%S); mkdir -p $BK
tar czf $BK/app-web.tar.gz server/app server/web README.md

# 1) 从 9951 同步代码（9951 是开发源，9952 是部署副本）
rsync -a --exclude __pycache__ --exclude '*.pyc' ../githubstar/server/app/ server/app/
rsync -a --exclude __pycache__ ../githubstar/server/web/ server/web/

# 2) 生效（bind mount，不用 build）
docker compose -p githubstar9952 restart api     # 约 3 秒

# 3) 验收（见第 4 节）
```

### 3.2 需要重建容器的情况

改了 `docker-compose.yml` 的 `environment` / `volumes` / `ports`，或改了 `.env` 的值（Token、账密、端口）：

```bash
docker compose -p githubstar9952 rm -sf api
docker compose -p githubstar9952 create api      # 按当前 .env 重建
docker compose -p githubstar9952 start api
```

> `restart` **不重读 `.env`** —— 症状是「配置改了但行为没变」。这是本项目最容易踩的坑。

### 3.3 需要重建镜像的情况（少见）

只有改了 `server/Dockerfile` 或 `server/requirements.txt` 才需要：

```bash
docker compose -p githubstar9952 build api
docker compose -p githubstar9952 rm -sf api && docker compose -p githubstar9952 up -d api
```

NFS 上重跑 pip install 通常 30~90 秒，比 `restart` 慢两个数量级 —— 不要拿它当日常操作。

### 3.4 回滚

```bash
# 代码回滚
tar xzf backups/code-<时间戳>/app-web.tar.gz -C .
docker compose -p githubstar9952 restart api

# 数据回滚（谨慎，会覆盖现库）
docker compose -p githubstar9952 stop api
docker exec -i ghradar-db-9952 psql -U postgres -d github < 备份.sql
docker compose -p githubstar9952 start api
```

镜像 tag 只有一个（`ghradar-api:9952`），**回滚代码靠 tar 包，不靠镜像** —— 所以 3.1 的第 0 步不要省。

## 5. 上线前必须拍板的一件事：9952 要不要自己采集？

**事实**：9952 的 `.env` 里有 40 字符的 `GH_GITHUB_TOKEN`，库里 `gh_app_setting.collect.token` 也有值，`scheduler.enabled=true`，`needs_token` 的三个任务（`collect_detail` / `collect_history` / `backfill`）当前 `last_run=None`（还没跑过）。

**风险**：9951 与 9952 用的是**同一个 GitHub 账号的同一个 Token**，额度 5000 次/小时是**账号级共享**的。两套都开自动采集 → 互相抢额度，症状是两边都出现 `403 API rate limit exceeded`、采集进度莫名停滞。

三个选项：

| 选项 | 做法 | 适用 |
|---|---|---|
| **① 9952 只读展示**（推荐用于演示/预览） | 关掉调度：`docker compose -p githubstar9952 exec -T db psql -U postgres -d github -c "UPDATE gh_app_setting SET value='false'::jsonb WHERE key='scheduler.enabled';"` 然后 `restart api` | 9952 只做页面预览，数据靠 9951 或手工同步 |
| ② 9952 独立采集 | 给 9952 换一个**独立账号**的 Token（写 `.env` 后重建容器） | 9952 要长期独立跑、自己积累历史 |
| ③ 保持现状 | 两套共用额度，接受偶发 403 | 只在临时验证期间可接受 |

> 这一项不拍板就上线，最可能的后果是**线上 9951 的采集被拖慢**，而不是 9952 报错。

## 6. 红线（每次操作前扫一眼）

1. **所有命令必须带 `-p githubstar9952`**。在 9952 目录里裸跑 `docker compose up -d` 会用默认项目名 `githubstar-9952`，**容器名冲突直接顶掉线上 `ghradar-api`**。
2. **禁止** `down -v` / `docker volume rm ghradar_pgdata_9952` —— 等于删库。
3. **禁止**改 9951 目录的任何文件（`githubstar/`），它是在线开发源；9952 只做「读取同步」，不做反向写。
4. 采集类任务在跑时**不要 `restart` / `rm` api 容器** —— 会 SIGKILL 掉容器内的采集进程（`EXIT=137`），进度停在半路。
5. 对外暴露前：改掉默认管理员账密（页面右上角「改账密」）、`GH_AUTH_SECRET` 设随机值、确认反代层有访问控制。
