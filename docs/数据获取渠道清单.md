# GitHub 飙升雷达 · 数据获取渠道清单

> 生成时间：2026-10-09　｜　文中所有「实测」均为本机真实执行结果，非推测。

## 0. 先纠正我之前的一个说法

我之前说过「GitHub 官方没有 star 历史接口」——**这话只对了一半**：

- ✅ **对的部分**：REST API 确实没有 `/repos/{o}/{r}/stargazers/history` 这类**聚合**端点，调它必然拿不到数据（应 404）。
- ❌ **漏掉的部分**：能拿到**每周 star 历史**的渠道远不止一种。除 REST 的 stargazers 分页外，还有 **GitHub GraphQL**、**GH Archive**、**ClickHouse 公开数据集**、**第三方聚合服务**。你的质疑是对的。

## 2. 项目当前**已实现**的渠道（逐条对应代码）

### 2.1 本地资料导入（离线，无网络）

`server/app/collectors/seed_importer.py`

| 入口 | 读什么 | 落到哪 |
|---|---|---|
| `import_index(seed_dir)` | 索引目录下 `repos.json` / `findarepo.json` / `search-merge.json` / `official.json` | `gh_repo`（各源指标取 max，`sources[]` 记来源，`seed_metrics{}` 留痕） |
| `import_local_history(seed_dir)` | `history/owner__repo.json`（文件名 `__` 代表 `/`） | `gh_repo_star_weekly` + `gh_repo_star_daily` |

首次建库由 `deploy/initdb/00-init.sh` 跑 `docs/sql/01-schema.sql` + `4-1..4-10`（`gh_repo` 全量 52,736 行，约 90MB）。

> ⚠️ `docs/sql/` 里 **只有 `gh_repo` 主表数据**，没有任何一张表的逐周明细（已核实：`4-1..4-10` 仅含 `INSERT INTO "gh_repo"`）。`02-seed-config.sql` 里的 `gh_stat_period` 只有 **14 条**周汇总，**W21~W27 官方压根没导出**——这正是首页柱状图那 7 个空柱的来源。

### 2.2 GitHub REST API（在线，计额度）

`server/app/collectors/github_client.py`

| 方法 | 端点 | 用途 |
|---|---|---|
| `repo()` | `GET /repos/{o}/{r}` | 仓库详情（stars/forks/lang/license/topics…） |
| `contributors()` | `GET /repos/{o}/{r}/contributors` | 贡献者（默认取 30） |
| `latest_release()` / `releases()` | `GET /repos/{o}/{r}/releases[/latest]` | 最新版本 / 最近 10 个版本 |
| `tags()` | `GET /repos/{o}/{r}/tags` | 无 release 时回退取 tag |
| `contents()` | `GET /repos/{o}/{r}/contents/{path}` | 目录列举（用于定位 README） |
| `readme()` | `GET /repos/{o}/{r}/readme` | README（base64 解码） |
| **`stargazers_history()`** | **`GET /repos/{o}/{r}/stargazers` + `Accept: application/vnd.github.star+json`** | **⭐ star 历史：每页 100 颗星带 `starred_at`，读 `Link: rel="last"` 拿总页数后从最后一页倒序回拉，整页早于 lookback 即停** |
| `search_repos()` | `GET /search/repositories` | 按 star 区间递归拆半收口全量仓库 |
| `rate_limit()` | `GET /rate_limit` | 额度查询 |

配套：
- `repo_collector._collect_one()` — 详情 + 贡献者 + 版本
- `history_collector.collect_one()` — 调 `stargazers_history()` → `_to_weeks()` 按 ISO 周（周一起）聚合 → 落库
- `search_harvester._harvest_range()` — `stars:lo..hi pushed:>=since fork:false archived:false` 递归拆半，每段 ≤1000 条
- 全局限速：`RateLimit` 类读 `X-RateLimit-*` 响应头；`RATE.exhausted()` 时置 `stop_flag` 立即停止，**不空转**
- 每线程独立 `requests.Session`；代理默认跟随系统/环境变量，显式 `GH_PROXY` 优先；403/429/5xx 指数退避；404 不算错误

### 2.3 raw CDN（**不计 API 额度**）

`github_client.readme_raw()` → `https://raw.githubusercontent.com/{full_name}/{branch}/{README.md|README.rst|…}`

### 2.4 本库内部派生（不联网）

| 方法 | 作用 |
|---|---|
| `facts_service.take_daily_snapshot()` | 把当前 star 落当日快照，`delta = 本日快照 − 上一次快照` |
| `facts_service.rollup_gains()` | 回填 `star_gain_1d/7d/30d/60d` 与 `daily_velocity`（要求窗口内至少 `max(2, days*0.6)` 天数据） |
| `facts_service.save_weekly()` / `save_daily_deltas()` | 官方历史 → 周事实 / 日事实 |
| `snapshot_service.compute_rank()` | 榜单快照计算与冻结 |
| `stat_service._fill_weeks()` | 把周序列补成连续，缺失周 `gain=0` 且标 `filled=True`（前端画成灰色柱子） |

## 3. 尚未接入、但**可用**的渠道（重点）

### 3.1 ClickHouse 公开数据集 ⭐ 最推荐

- **地址**：`https://play.clickhouse.com/`，账号 `explorer`（密码空），表 `github_events`
- **规模**：**111.8 亿条**事件，覆盖 `2011-02-12 ~ 2026-10-09`
- **star 事件**：`event_type = 'WatchEvent'`，共 **5.55 亿**条
- **本机实测**：

| 测试 | 结果 |
|---|---|
| 数据集时间范围 | `2011-02-12 00:00:00 ~ 2026-10-09 02:59:59`，`count()=11,182,167,092` |
| 单仓库按周聚合（torvalds/linux，近 8 周） | 正常返回，如 `2026-09-13 → 146 颗` |
| 多仓库 × 周聚合（5 仓库近半年） | 返回 132 行 |
| 单查询耗时 | **0.31s** |
| **8 线程并发**（8 个月份各查一次） | 总耗时 **0.72s**，无失败 |
| 查询缺失区间 W21~W27（2026-05-18~07-05） | **有数据**（如 build-your-own-x 等四仓合计 555/629/691/509/315/241/178/177 颗） |

- **限制**：官方说明「公共 playground，资源有限、公平使用」，不适合超大并发；查询需 `FORMAT TSV/JSON` 明确输出格式。
- **价值**：**这是唯一能一次性补齐任意仓库任意历史周增量的免费渠道**，不必逐仓翻页。

### 3.2 GH Archive

- **地址**：`https://data.gharchive.org/{YYYY-MM-DD}-{0..23}.json.gz`
- **内容**：每小时的全量公开 GitHub 事件（含 `WatchEvent`），**2011-02 至今**
- **本机实测**：`GET 2024-06-01-0.json.gz` → **HTTP 200**，`content-length: 75,773,379`（单小时约 75MB）
- **限制**：无配额，但文件大、需自行解析聚合；适合批量离线重建，不适合交互式查询。

### 3.3 GitHub GraphQL API

- **端点**：`POST https://api.github.com/graphql`
- **能力**：`repository(owner,name){ stargazers(first:100, after:$cursor){ edges{ starredAt } } }` —— 单请求 100 条带 `starredAt`，**游标分页**（比 REST 的页码翻页更稳）
- **额度**：**5,000 点/小时，与 REST 的 60/h 分开计算**（有 token 时）
- **本机实测**：未认证 `POST /graphql` → **HTTP 403**（必须有 token）

### 3.4 star-history.com

- **地址**：`https://api.star-history.com/svg?repos={o}/{r}&type=Date`
- **实测**：**HTTP 200**（返回 SVG；同站点另有 JSON/embed 形式）
- **限制**：第三方服务，无 SLA，聚合口径不透明，仅适合展示、不适合入库。

### 3.5 OSS Insight

- 有公开 API（`api.ossinsight.io`），实测我拼的路径 `GET /v1/repos/{owner}/{repo}/` 返回 **404**，需查阅其文档确认正确端点后使用。

## 4. 补全首页柱状图缺失周（W21~W27）的可执行方案

**结论：用 3.1 的 ClickHouse 公开数据集，多线程批量补齐。**

### 为什么是它

- W21~W27（2026-05-18 ~ 2026-07-05）在**源资料里根本不存在**（不是程序 bug、不是查询写错），只能从外部拿。
- 走 REST `stargazers` 逐仓翻页：52,736 个仓库 × 平均多页 × 60 次/小时额度 → **不可行**。
- ClickHouse 一次 SQL 就能按周聚合，实测 8 并发 0.72s。

### 步骤

1. 从 `gh_repo` 取 `full_name`（52,736 个），按批（建议 300~500 个/批）拼 `IN (...)`。
2. 查询模板（周一起算，与项目 `_to_weeks` 的 ISO 周口径一致）：

```sql
SELECT repo_name,
       toStartOfWeek(created_at) AS wk,
       count() AS stars
FROM github_events
WHERE event_type = 'WatchEvent'
  AND repo_name IN (<批量仓库名>)
  AND created_at >= '<起>' AND created_at < '<止>'
GROUP BY repo_name, wk
ORDER BY repo_name, wk
FORMAT TSV
```

3. 结果写入 `gh_repo_star_weekly`（`weekly_new`=该周 stars）与 `gh_stat_period`（`period_type='week'`、`gain_sum`=该周全库合计），随后调 `facts_service.rollup_gains()`。
4. 多线程并发（实测 8 线程无失败），每批带重试与限速（playground 是公共资源，建议并发 ≤8、批间加小睡）。
5. 补完后前端柱状图那 7 个 `filled=True` 的灰柱会自动变成真实数据。

### 校验口径

- 补全后 `SUM(gh_repo_star_weekly.weekly_new)` 与 ClickHouse 直接 `count()`（按同一周）应对得上。
- 注意 `created_at` 是 **UTC**，项目周起点为**周一**，两边取整方式要保持一致。

## 5. 已知的坑（踩过的）

1. **匿名 REST 额度只有 60 次/小时**，且每个 IP 独立；本机实测当前 `core.remaining = 0`（已用 60）。批量采集前必须配 `GH_GITHUB_TOKEN`。
2. **`gh_repo_star_daily.delta_stars` 全为 0**：库里只有一天快照，没有"前一天"可比 → 事实口径 `HAVING SUM(delta_stars)>0` 会把结果全滤掉。已修：`_has_daily_fact()` 改为要求存在**非零 delta**。
3. **`star_gain_1d` / `daily_velocity` 全为 0**（实测 `0 | 6065 | 7843 | 8668`）：日粒度需连续两天快照才有值，所以日榜退用「近 7 天日均」折算（`source=rollup_avg7`）。
4. **源资料只导 `gh_repo` 主表**，事实表全靠运行时累积或外部补齐。
5. ClickHouse playground 是**公共资源**，请限速使用，不要把它当生产库压测。
