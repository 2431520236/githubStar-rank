## 一、总览：三层缓存

| 层 | 位置 | 作用 | 失效方式 |
|---|---|---|---|
| **L1 服务端内存缓存** | `app/cache.py` | 命中后完全不查库 | TTL 到期 或 任务收尾 或 管理员手动清 |
| **L2 浏览器校验缓存** | `main.py` `NoCacheStaticFiles` / `ETagMiddleware` | 回源只传响应头（304），body 0 字节 | 文件/内容变化 → ETag 变 |
| **L3 传输压缩** | `main.py` `GZipMiddleware` | 传输体积 -70%~-85% | 无（每次压缩） |

## 二、L1：服务端内存缓存（`server/app/cache.py`）

### 实现
零依赖、纯 stdlib 的 TTL 字典缓存（**没有引入 Redis** —— 用户要求"最轻量、如 SpringBoot Cache"）：

```python
@cache.cached(ttl=300)      # 装饰在路由函数上
def overview(): ...

cache.invalidate()          # 全清
cache.invalidate("stats")   # 按子串清
cache.size()                # 当前条目数
```

- 缓存 key = `函数限定名 + 全部参数(JSON 序列化)` → **不同查询条件天然各自缓存**。
- 最多 512 条，超量淘汰最早到期项；读取时惰性清理过期条目。

### TTL 策略（`config.py`，环境变量可覆盖）★2026-10 用户重定

**两档制**，所有接口统一适用：

| 场景 | 判定 | TTL | 环境变量 |
|---|---|---|---|
| **无条件 / 默认视图** | 全部入参都等于各自默认值 | **600s（10 分钟）** | `GH_CACHE_TTL_DEFAULT` |
| **带条件的查询** | **任一**入参偏离默认值（`q=`、`langs=`、`min_stars=`、`period_key=`、`year=`、`page=2`…） | **120s（2 分钟）** | `GH_CACHE_TTL_COND` |

> 用户逐字口径：「我说的 10 分钟缓存，包含所有接口；带条件的查询，可以缓存 2 分钟。」
>
> 实现：`cache.cached()` 用 `inspect.signature` 提取每个参数的**默认值**（自动解包 FastAPI 的
> `Query(1)` → `1`），与 FastAPI 传入的实参逐一比对；只要有一个不等，就判定为「带条件」→ 用短 TTL。
> 因此同一接口的「默认视图」与「筛选结果」各自独立缓存、TTL 不同。
>
> 实测：`demo()` → TTL 600.0s，`demo(a=5)` → TTL 120.0s（两档并存）。

书写方式统一为 `@cache.cached()`（不传参即取上面两个默认值）。

### 失效时机（用户口径：「触发任务的话，任务执行结束清理一次缓存即可」）

任务收尾统一清一次**全量**缓存，共四处落点：

1. `services/job_service.py` 的 `job()` finally —— 采集/rollup 等走 job 的任务
2. `services/scheduler.py` 的 `_spawn()` finally —— 定时任务
3. `api/system_controller.py` 的 `_spawn_bg()` finally —— 后台线程任务
4. `api/rank_controller.py` 的 `ranks/compute`、`ranks/ensure`、`ranks/compute-all` 返回前

外加**管理员手动清**：`POST /api/system/cache/invalidate?pattern=`（pattern 可选）。

### 权限与缓存的关系（用户 2026-10 定）

> 「用户和管理员只是页面权限差异，数据相同，都应该走缓存。」

- 缓存挂在**接口层**，`/api/ranks`、`/api/stats/*` 等对所有人返回同一份数据 → 天然共用同一缓存，
  不会因 `is_admin` 分叉，也不会重复查库。
- 权限差异只体现在**页面显隐**（`v-if="auth.isAdmin"`）与**写操作**（`admin_guard` 中间件）。
- 唯一例外是 `/api/watch/list`（管理员看后台关注列表）—— 数据本身因人而异，故不缓存。

## 三、L2：浏览器校验缓存

### 静态资源：分两类策略 ★2026-10 用户重定（「很多资源不必重复下载」）

`main.py` 的 `NoCacheStaticFiles` 按路径前缀区分：

| 类型 | 路径 | 响应头 | 效果 |
|---|---|---|---|
| **第三方库** | `/web/vendor/*`（vue / element-plus / echarts，约 **1.4 MB**，几乎不变） | `public, max-age=31536000, immutable` | **浏览器直接用本地副本，完全不发请求** —— 真正「不必重复下载」 |
| **业务文件** | `/web/js/*`、`/web/css/*`（自写脚本样式，改版频繁） | `no-cache, must-revalidate` + ETag | 存副本、每次回源校验；没变 **304**（body 0 字节），一改立刻生效 |
| **页面** | `/`、`*.html` | `no-cache, must-revalidate` + ETag | 同上（比改造前的 `no-store` 省 8KB/次） |

- **为什么 vendor 用强缓存**：这 1.4 MB 是首屏最大头，且升级频率极低。给它 1 年强缓存后，
  回访用户一个字节都不下载。
- **升级 vendor 库时**：改 `index.html` 里的引用加版本参数（如 `?v=2`）即可强制刷新
  —— 带 query 的 URL 被视为不同资源。改动方式见 `web/index.html`。
- ⚠️ 曾把 `is_not_modified` 重写为 `return False`（禁用 304），必须删除该重写，否则 304 永不生效。

### API 响应：`ETagMiddleware`

`main.py` 的 `ETagMiddleware` 给 `/api/` 的 200 GET JSON 响应算 `md5` 作为强 ETag：

```
ETag: "5fc3295f..."
Cache-Control: no-cache, must-revalidate
```

下次同请求带 `If-None-Match` → 返回 **304**。

### 页面（HTML）能不能浏览器缓存？★2026-10 补充

**能，但取决于「响应是否因人而异」**——这是唯一的判据：

| 场景 | 能否公共缓存 | 正确做法 |
|---|---|---|
| **静态页面**（同一 HTML 发给所有人，登录态/权限由前端 JS 决定）← **本项目** | ✅ 能 | `no-cache` + ETag（存副本 + 回源校验 → 304） |
| 几乎不变的页面 | ✅ 能，且可强缓存 | `public, max-age=N`（改版后最多 N 秒生效） |
| **动态页面**（标题/内容随登录用户变化、或页面内嵌 per-session token） | ❌ 公共缓存会串号 | `private, no-cache`（只允许浏览器存）或 `no-store` |

四种指令的取舍：

| 响应头 | 语义 | 适用 |
|---|---|---|
| `no-store` | **完全不存**（每次全量重下） | 含敏感信息、每次都必须最新 |
| `no-cache` | 存，但**每次回源校验**（没变 → 304） | 要「即时生效」又要省流量 ← **本项目页面与业务 JS/CSS** |
| `public, max-age=N` | N 秒内**直接用副本、不发请求** | 几乎不变 ← **本项目 vendor 库** |
| `private, max-age=N` | 只浏览器可存，CDN/代理不存 | 个人化但变化慢（如「我的订单」） |

**本项目关键设计**：页面 HTML **不含任何因人而异的内容**——权限/登录态由 `GET /api/auth/me` 返回角色、前端 `v-if` 控制显隐。所以同一份 HTML 可以安全地发给所有人，天然可公共缓存。要把个性化数据做成 HTML，就必须放弃页面缓存。

#### ⚠️ 踩坑：`FileResponse` 不做 304 判定（实测）

页面原先直接 `FileResponse(html)`，响应头**有 ETag**，但带 `If-None-Match` 复请仍返回 **200 全量 8.8KB**。
原因：Starlette 的 `FileResponse` 只**设置** `ETag`/`Last-Modified` 头，
**304 的判定逻辑在 `StaticFiles.is_not_modified()` 里**，`FileResponse` 不涉及。
修法：在页面路由里自己算 ETag 并比对（`main.py` 的 `_page()`），实测修复后 6 个页面 + `/detail` 复请全部 **304 / 0 字节**。

`StaticFiles` 挂载的静态资源不受此问题影响（它自带 304 判定）——这也是为什么 `js/css` 早就 304、而页面没有。

**中间件顺序（关键）**：`add_middleware` 后加的在**外层**。当前顺序：

```
add(ETagMiddleware) → add(GZipMiddleware)
请求方向: anti_scrape → admin_guard → GZip → ETag → CORS → 路由
```

GZip 在最外层 → ETag 在它**内层** → ETag 基于**未压缩** body 计算，跨客户端（不同
`Accept-Encoding`）稳定，不会因为压缩结果不同导致 ETag 抖动。

## 四、L3：GZip 压缩（`GZipMiddleware`，`minimum_size=500`）

实测效果：

| 资源 | 原始 | gzip 后 | 压缩率 |
|---|---|---|---|
| `element-plus.full.min.js` | 957,516 B | 286,302 B | **-70%** |
| `/api/ranks`（JSON，未压缩时 157~308 KB） | — | — | JSON 文本压缩率通常 **-80%+** |

小于 500 字节的响应不压缩（如 `overview` 只有 420 B，压缩后可能反而变大）。

### ⚠️ gzip 的缺点（用户询问）

| 缺点 | 说明 | 本项目影响 |
|---|---|---|
| **CPU 开销** | 每个响应都要压缩。等级越高越慢 | 默认等级 9 偏高；4C4G 下建议降级。当前用 Starlette 默认（9），后续可换 `compression_level=6` |
| **对已压缩格式无收益甚至变大** | `.jpg/.png/.woff2/.zip/.mp4` 本身已压缩，再 gzip 体积略增 | 本项目 vendor 只有 js/css（文本），**无此问题**；但将来加图片要注意 `GZipMiddleware` 按 content-type 跳过 |
| **BREACH 攻击面** | 攻击者可控输入 + 响应含秘密（如 CSRF token）时，可通过压缩长度侧信道推断秘密 | 本项目无 per-request 秘密混在压缩响应里；且会话走 HttpOnly Cookie 不反射到 body。风险低，但**不要把 token 写进响应体** |
| **首字节延迟（TTFB）** | 需等整个响应体生成完才能压缩（非流式） | 我们的接口都是小 JSON，无影响；**大文件流式下载会被拖慢**（本项目无此场景） |
| **老客户端兼容** | 极老的客户端不认 `Content-Encoding: gzip` | 现代浏览器全支持，忽略 |
| **代理/CDN 二次压缩** | 中间层可能重复压缩或剥离 | 若前置 Nginx，应让 Nginx 负责 gzip 并关闭应用层，避免重复 |

**结论**：对本项目（大量文本 JSON + 2.4 MB 的 JS/CSS，无图片大文件、无流式下载）收益远大于成本。
唯一要留意的是 4C4G 下压缩等级，可降到 6 换取 CPU。

## 四点五、IP 频率限制（`app/rate_limit.py`）★2026-10 用户要求，**默认启用**

用户口径：「同一个接口但是可能有很多人不同条件，增加 ip 限制查询频率，防止恶意狂刷，
默认同一接口最快 1 秒一次，所有接口 20 次秒，同一 ip 下」。

| 规则 | 阈值 | 说明 |
|---|---|---|
| **同一接口** | **1 次/秒**（同 IP） | path **不含 query** —— 不同查询条件算「同一接口」，防止「同 IP 换参数狂刷同一接口」 |
| **全部接口合计** | **20 次/秒**（同 IP） | 1 秒滑动窗口兜底，防脚本轮询 |

- 实现：纯内存 `defaultdict` + 时间戳（零依赖，单 worker 准确）。被限返回 **429**
  `{"code":429,"msg":"请求过于频繁，请稍后再试"}` + `Retry-After: 1`。
- 只约束 `/api/`；**静态资源、页面、`/robots.txt`、`/docs` 不在限流范围**
  （否则首屏并发加载静态资源会被误伤）。
- 位置：**最外层中间件**（最后定义 ⇒ 最先执行），恶意请求尽早被挡。
- **探针豁免**：`/api/system/health`、`/api/system/rate-limit`、`/api/auth/me` 豁免「同接口 1 次/秒」，
  但仍计入全局 20 次/秒 —— 因为每次页面加载「顶栏组件」与「页面脚本」会各调一次
  （实测首页仅 health 就 2 次），不豁免会让正常首屏出现 429。
- 前端配合：`app-common.js` 的 `req()` 把 `code` 挂到 Error 上；`screen.js` 的
  `loadScreen` / `loadRanks` 遇 **429 静默保留旧数据**，不弹错误。
- 调参：`GH_RATE_LIMIT_ENABLED`（默认 true）、`GH_RATE_LIMIT_PATH_PER_SEC`（默认 1）、
  `GH_RATE_LIMIT_GLOBAL_PER_SEC`（默认 20）。
- 实测：同接口 1 秒内两次 → `200, 429`；探针连打两次 → `200, 200`；
  并发 30 个不同 path → `200×19 + 429×10`（命中 20 上限）。

## 六、容量评估：4C4G + 20Mbps 带宽

### 实测基线（本机 28 核 / 70G，热数据全在内存）

| 接口 | 并发 20 | 并发 40 | 并发 80 |
|---|---|---|---|
| `/api/stats/overview`（缓存命中） | 585 QPS / P50 33ms | 571 QPS / P50 67ms | 577 QPS / P50 135ms |
| `/api/ranks`（打表，改造前） | 167 QPS / P50 12ms | 198 QPS / P50 72ms | 213 QPS / P50 197ms |

全部并发档位 **0 错误**。

### 4C4G 推算

| 类型 | 本机 | 4C4G 估算 |
|---|---|---|
| 命中缓存接口 | 577 QPS | **250~350 QPS** |
| 打表接口（热） | 213 QPS | **50~100 QPS** |
| 打表接口（冷盘） | 5 QPS | **1~3 QPS** |

- uvicorn 单进程 → HTTP/序列化只吃 1 核。
- PG 在 4G 内存下已调优（见下），冷盘惩罚大幅缓解。
- **结论：4C4G 下持续 100~300 QPS 无压力，瞬时并发 50 不报错。**

### 带宽账（20 Mbps = 2.5 MB/s）

| 方案 | 首屏静态 | 首屏 API | 合计 | 20M 同时开放 |
|---|---|---|---|---|
| 改造前 | 2.4 MB（每次重下） | ~0.7 MB | 3.1 MB | ~2 人 |
| 改造后 + gzip | ~0.6 MB | ~0.1 MB | **0.7 MB** | **~10 人** |
| 改造后 + 回访（304） | **0** | ~0.02 MB | **~0.02 MB** | 几乎无限 |

> **关键判断：20M 带宽下瓶颈是带宽，不是数据库。** 改造前 3 人同时刷新首页就把带宽占满，
> 而 DB 只用了 200 QPS 能力的零头。

### 为什么不加 uvicorn 多 worker（结论：暂不做）

`uvicorn.run(..., workers=N)` 会带来两个**破坏性问题**：

1. **调度器重复启动**：`scheduler` 在 lifespan 里随每个 worker 各起一份 → 采集/榜单计算重复执行、重复写库。
2. **内存缓存分裂**：每个 worker 一份 `_MEMO`，缓存命中率降到 1/N。

若将来确需多 worker，必须先做两件事：① 用文件锁/独立进程把 scheduler 拆出去（只留一份）；
② 缓存换 Redis 共享。当前收益（HTTP 吞吐 ×1.8）不值得这个复杂度。

## 七、PostgreSQL 调优（`docker-compose.yml`）

```yaml
command: >
  postgres
  -c shared_buffers=1GB            # 默认 128MB, 装不下工作集 → 冷查询 2 秒
  -c effective_cache_size=3GB
  -c work_mem=16MB
  -c maintenance_work_mem=256MB
  -c max_connections=100
  -c random_page_cost=1.1          # SSD/NFS 随机读代价
  -c log_min_duration_statement=1000
```

- 生效需**重建 db 容器**：`docker compose rm -sf db && docker compose create db && docker compose start db`
  （数据在命名卷 `ghradar_pgdata`，安全）；重建后**必须重启 api**（旧连接池连接已失效）。
- 实测生效：`SHOW shared_buffers` = 1GB，`SHOW effective_cache_size` = 3GB。
- ⚠️ 参数按 **4G 内存目标机**设定。若部署在更大内存机器上，可等比上调。

## 九、调试开关（便于开发，不仅生产性能）★2026-10 用户要求

每一层优化都是**可分档开关**，可在**不重启、不改代码**的情况下独立开合 —— 开发时一键关掉，
拿最新数据 / 不被 429 / 看原始响应；生产时全开。

### 开关清单（存 `gh_app_setting`，key 前缀 `debug.*`，改完**立即生效**）

| key | 默认 | 关掉后 |
|---|---|---|
| `debug.cache_enabled` | true | **直通**：不读不写缓存，每次查库（`X-Cache: BYPASS`） |
| `debug.rate_limit_enabled` | true | 不限流，不再返回 429（便于压测/开发） |
| `debug.gzip_enabled` | true | 不压缩，返回原始未压缩响应 |
| `debug.etag_enabled` | true | 不加 ETag、不做 304，每次 200 全量 |
| `debug.static_cache` | true | 静态资源退化为 `no-store`（便于反复刷新验证首屏） |
| `debug.response_headers` | true | 不返回 `X-Cache` 等调试响应头（完全静默） |

### 三种调试手法

**1. 响应头（最快，一眼看出走没走缓存）**

```
X-Cache: HIT | MISS | BYPASS      ← 本次请求的缓存结果
X-Cache-TTL: 597.3                ← 命中时的剩余 TTL（秒）
X-Debug-Flags: all-on             ← 当前被**关闭**的开关名；全开时为 all-on
```

**2. 调试接口（需管理员）**

| 接口 | 作用 |
|---|---|
| `GET /api/system/debug/status` | 全部开关当前值 + 缓存命中/未命中/直通次数 + 命中率 + 两档 TTL + 限流额度 |
| `GET /api/system/debug/cache/entries` | 缓存条目明细（key 截断 + 剩余 TTL），确认「哪个接口真被缓存了」 |
| `POST /api/system/debug/flags` | 快速切开关，body `{"key":"debug.cache_enabled","value":false}` |
| `POST /api/system/debug/cache/reset-stats` | 重置命中统计（便于对照实验） |
| `POST /api/system/cache/invalidate` | 清空缓存（管理员顶栏「清理缓存」按钮也走这个） |

**3. 前端调试面板**

浏览器打开 `?debug=1`（或控制台 `Radar.debug.set(true)`）→ 右下角浮出面板：

```
调试面板 · X-Cache
命中 3 / 未命中 2 / 直通 0
MISS 600s /api/stats/screen?exclude_major=false
HIT  597s /api/stats/screen?exclude_major=false
MISS 120s /api/ranks?metric=total&page_size=100...
```

同时 `Radar.debug.status()` 在控制台打印服务端开关与缓存状况（`console.table`）。
关闭：`Radar.debug.set(false)`。生产不开启时**零开销**（只是 URL 一次正则判断）。

### ⚠️ 两个实测踩到的坑

1. **限流会把调试接口自己挡住** —— 「用 `/api/system/debug/flags` 去关限流」时，
   连续调用会被「同接口 1 次/秒」规则 429，开关根本没写进库（症状：改了开关行为不变）。
   修法：`rate_limit.EXEMPT_PREFIXES` 把 `/api/system/debug` 整段前缀豁免单接口规则
   （仍计入全局 20 次/秒）。
2. **contextvar 在线程池里传不回来** —— 想在路由（同步 `def`，跑在 anyio 线程池）里
   `_LAST.set(结果)`，外层中间件**读不到**（实测恒为 None）：因为 anyio 是**浅拷贝** context 到线程。
   修法：ContextVar 里放一个**可变 dict**，中间件 `_LAST.set({})` 建它，
   路由线程 `mark()` 往同一个 dict 里写 —— 引用被拷贝、对象共享，外层就能读到。

   同理，**调试面板里的 `X-Cache` 就是靠这个机制**才能出现在响应头上。
