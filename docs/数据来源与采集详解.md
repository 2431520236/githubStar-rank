## 0. 总览：数据从哪来、怎么流

```
源资料(SQL 快照)  ──initdb──►  gh_repo 主表(52736 行)  ──┐
                                                        ├──►  gh_repo_star_weekly ──► rollup ──► star_gain_1d/7d/30d/60d
GitHub REST API   ──采集器──►  详情/README/参与者/版本      │                                        │
                                                        ├──►  gh_repo_star_daily  ────────────────┼──► /api/ranks 榜单
ClickHouse 公共集 ──脚本───►  star 历史(按天→按周)          │                                        │
                                                        └──►  gh_stat_period(周/月汇总)  ──────────┴──► 大屏图表
AI 概要(LLM)      ──任务───►  gh_repo.ai_summary  ──► 列表/详情的「概要」列
```

四类数据源，用途完全不同：

| 源 | 作用 | 是否可批量 | 备注 |
|---|---|---|---|
| **源资料 SQL 快照** | 一次性导入 5.2 万仓库的**静态元数据**（star 数、语言、协议、描述…） | ✅ 一次性 | `docs/sql/4-1..4-10`，约 90MB |
| **GitHub REST API** | 增量更新元数据、README、参与者、版本；单仓 star 历史 | ⚠️ 逐仓 | 匿名 60 次/小时；配 token 5000 次/小时 |
| **ClickHouse 公共数据集** | **批量补 star 历史**（多仓 × 多天一次拿完） | ✅✅ 一次 500 仓 | `play.clickhouse.com`，免 key |
| **LLM（供应商模型）** | 生成中文概要 | ✅ 分组批量 | 需先在「模型与任务」页配供应商 |

## 一、数据源明细

### 1.1 源资料 SQL 快照（首次导入）

- 位置：`docs/sql/`
  - `01-schema.sql` —— 建 16 张表
  - `02-seed-config.sql` —— 配置/任务/白名单/周期 种子
  - `4-1` ~ `4-10` —— `gh_repo` 全量数据，共 **52,736 行**（约 90MB）
- 触发：`docker compose up -d` 首次启动时由 `deploy/initdb/00-init.sh` 自动执行；
  卷里写 `.init_done` 哨兵，**之后永不重跑**。
- 手工重跑：`docker compose exec api python3 tools/load_data.py --seed-dir /seed`
- ⚠️ 源文件里 JSONB 列被导成 SQL 裸字面量（`1095` / `TRUE` / `https://…`），PG15 会拒绝；
  `tools/load_data.py` 会自动改写为合法 JSON，**不改动原始资料**。

### 1.2 GitHub REST API（增量采集）

- 基址：`GH_API_BASE`，默认 `https://api.github.com`（配置项见 `server/app/config.py`）
- 鉴权：`GH_GITHUB_TOKEN`；**为空时匿名限速 60 次/小时**，批量采集不可行
- 并发/超时/重试：`GH_CONCURRENCY=6`、`GH_REQUEST_TIMEOUT=25`、`GH_MAX_RETRIES=3`
- 用到的端点：

| 端点 | 用途 | 实现 |
|---|---|---|
| `GET /repos/{o}/{r}` | 仓库详情（star/fork/语言/协议/topics） | `github_client.repo()` |
| `GET /repos/{o}/{r}/readme` | README 文本（喂给 LLM） | `github_client.readme()` |
| `GET /repos/{o}/{r}/contributors` | 参与者 Top 30 | `github_client.contributors()` |
| `GET /repos/{o}/{r}/releases` | 版本记录（默认 10 条） | `github_client.releases()` |
| `GET /repos/{o}/{r}/contents/{path}` | README 地址探测 | `github_client.contents()` |
| `GET /repos/{o}/{r}/stargazers` | **单仓 star 历史**（见下） | `github_client.stargazers_history()` |
| `GET /search/repositories` | 全量收口（区间递归拆半） | `search_harvester.harvest()` |

**单仓 star 历史的正确姿势**（`stargazers_history`，`per_page=100`、`max_pages=60`）：

1. 必须带请求头 `Accept: application/vnd.github.star+json` —— 每项才有 `starred_at` 时间戳；
2. 该接口按 `starred_at` **升序**返回（最新在最后一页）；
3. 先读响应头 `Link: rel="last"` 拿到总页数，**从最后一页倒序往前拉**，整页都早于 `since` 即停；
4. 额度耗尽（`RATE.exhausted()`）立刻中断，已拉到的部分照常落盘。

> 注意：GitHub **没有** `/stargazers/history` 聚合端点，调它必然 404。

### 1.3 ClickHouse 公共数据集（批量补 star 历史）★主力

- 地址：`https://play.clickhouse.com/`，账号 `explorer`，**无需密码**
- 表：`github_events` —— 111.8 亿条事件，覆盖 **2011-02-12 至今**；`event_type='WatchEvent'` 即 star 事件
- 查询方式：HTTP POST，`?user=explorer&default_format=TSV`，SQL 放 body
- **批量姿势**：一次请求塞一批 `repo_name`（默认 **500 个**），SQL 只取三个字段：

```sql
SELECT repo_name, toDate(created_at) AS d, count() AS n
FROM github_events
WHERE event_type = 'WatchEvent'
  AND repo_name IN ('owner/a','owner/b', ... 最多 500 个 ...)
  AND created_at >= now() - INTERVAL 400 DAY
GROUP BY repo_name, d
FORMAT TSV
```

- 实测：100 仓 = 1 次请求，返回 5,117 条周记录 / 30,601 条日记录，**含写库 2 秒**。
- 回溯窗口：`LOOKBACK_DAYS = 400`（约 13 个月）。要更早的历史需调大该常量。

### 1.4 备用渠道（当前未启用）

| 渠道 | 能力 | 备注 |
|---|---|---|
| GH Archive | `data.gharchive.org/{YYYY-MM-DD}-{0..23}.json.gz`，每小时全量事件 | 无额度限制，单小时文件约 75MB |
| GitHub GraphQL | `stargazers(first:100, after:$cursor){edges{starredAt}}` | 5000 点/小时，与 REST 分开计；无 token 返回 403 |
| star-history.com | `api.star-history.com/svg?repos=o/r` | 第三方，口径不透明，仅供展示 |

## 二、数据表字典（16 张表）

### 2.1 `gh_repo` —— 仓库主表（52,736 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | 内部主键 |
| `full_name` | text | `owner/name`，全局唯一 |
| `owner` / `name` | text | 拆分 |
| `html_url` / `api_url` / `readme_url` | text | 各类地址 |
| `description` | text | GitHub 官方简介 |
| `summary` / `ai_summary` | text | 概要（后者由 LLM 生成，中文） |
| `ai_summary_tries` | int | 生成尝试次数，**上限 3**，超过不再重试 |
| `lang` | text | 主语言 |
| `license_spdx` / `license_name` | text | 协议 |
| `topics` | jsonb | 标签数组 |
| `stars` / `forks` / `watchers` / `open_issues` | int | 当前计数 |
| `contributors_count` | int | 参与者数 |
| `latest_version` / `version_note` / `latest_release_at` | text/ts | 最新版本 |
| `is_major` | bool | 是否命中**熟知名单**（可过滤） |
| `is_archived` | bool | 已归档 |
| `star_gain_1d` / `star_gain_7d` / `star_gain_30d` / `star_gain_60d` | int | **滚动增量**，由 `rollup_gains()` 从事实表算出 |
| `history_synced_at` | ts | 上次 star 历史同步时间；**为 NULL 说明从未采集过** |

### 2.2 `gh_repo_star_weekly` —— 每周 star 事实（榜单基础）

| 字段 | 说明 |
|---|---|
| `repo_id` + `week_start` | **联合唯一约束 `uq_gh_star_weekly`** —— 去重的根本保证 |
| `week_key` / `week_label` / `week_index` | `2026-W40` / `W40` / `40` |
| `weekly_new` | 该周新增 star |
| `cumulative` | 该周结束时的累计 star（由当前 `gh_repo.stars` 往前逐周反推） |
| `days` | jsonb，按天明细 `[{"day":"2026-09-28","count":19}, ...]` |
| `source` | `stargazers_history`（官方接口）/ `clickhouse_gh_events`（公共数据集） |

### 2.3 `gh_repo_star_daily` —— 每日 star 事实

`repo_id` + `stat_date`（联合唯一 `uq_gh_star_daily`），含 `stars` / `forks` / `watchers` / `open_issues` 及各 `delta_*` 增量。

### 2.4 `gh_stat_period` —— 周/月汇总元信息

`period_type`（`day`/`week`/`month`）、`period_key`、`period_start`、`period_end`、`is_complete`、`is_locked`、`repo_count`、`gain_sum`。

> 源资料自带 **14 周真实 `gain_sum`**（W20 + W28~W40），是柱状图的**降级数据源**。

### 2.5 其余表

| 表 | 用途 |
|---|---|
| `gh_repo_contributor` | 参与者（login/avatar/contributions/rank_no） |
| `gh_repo_release` | 版本记录 |
| `gh_rank_snapshot` | 榜单快照（冻结）。约束 `CHECK (metric IN ('total','gain'))` |
| `gh_rank_whitelist` | 熟知名单/黑名单（`list_type = major \| block`） |
| `gh_app_setting` | 应用配置（key-value jsonb） |
| `gh_llm_provider` / `gh_llm_model` | LLM 供应商/模型（**只读不写**，真源是 `server/data/llm_config.json`） |
| `gh_llm_task` | 固定任务定义（含提示词模板、并发、批大小） |
| `gh_llm_run` | AI 执行记录（tokens/延迟/错误） |
| `gh_watch_target` / `gh_watch_event` | 关注提醒目标与事件 |
| `gh_job_log` | 采集任务日志 |

## 三、采集与拉取策略

### 3.1 三条采集线

| 线 | 入口 | 拉什么 | 限速/节流 |
|---|---|---|---|
| 详情补全 | `POST /api/system/collect/details` | 仓库详情、参与者、版本 | 线程池并发 `concurrency`（默认 6） |
| README 地址 | `POST /api/system/collect/readme` | README 文本（喂 LLM） | 并发 6，`refresh_after_days` 默认 30 |
| star 历史 | `POST /api/history/collect` 或 ClickHouse 脚本 | 每日/每周 star 增量 | 官方接口并发 3，`refresh_after_days` 默认 7 |
| 全量收口 | `POST /api/system/harvest-search` | `search/repositories` 区间递归拆半，把全库补全 | 后台线程，单例防重入 |
| 一键刷新 | `POST /api/system/refresh` | 三步：补 star 历史 → 全量收口 → 缺口批量补齐 | 后台线程 |

### 3.2 候选挑选（每次拉谁）

`repo_service` 里三套候选 SQL，都带 `LIMIT`：

- `candidates_for_detail(limit=100, only_missing=True)` —— `ORDER BY stars DESC`
- `candidates_for_history(limit=200, refresh_after_days=7)` —— `ORDER BY star_gain_7d DESC NULLS LAST, stars DESC`
- `candidates_for_readme(limit=200, refresh_after_days=30)` —— `ORDER BY stars DESC`

> `only_missing=True` 时只挑 `history_synced_at IS NULL` 或超过重采天数的。这是**业务层防重复拉取**的第一道闸。

### 3.3 ClickHouse 批量补历史（主力）

脚本：`server/tools/backfill_star_history.py`

```bash
# 全量、只补缺失、真正写库
docker compose exec -T api python3 tools/backfill_star_history.py --limit 0 --only-missing --write
```

| 参数 | 含义 | 默认 |
|---|---|---|
| `--limit N` | 取 star 最高的前 N 个仓库；**0 = 全量** | 500 |
| `--batch N` | **一次请求塞多少个 repo_name**（多项目） | 500 |
| `--workers N` | 并发批数 | 4 |
| `--only-missing` | 只挑库里还没有周记录的仓库（业务层防重复） | 关 |
| `--write` / 不加则试跑 | 是否真正写库 | 关 |

**为什么快**：一次请求塞 500 仓，SQL 只取 3 个字段，按天聚合返回；Python 侧再按 ISO 周汇总。
**内存**：批拉批写、流式处理，内存峰值 = 一批的量，不随库规模增长。
**写入**：每 1000 行拼一条多值 `INSERT ... VALUES (...),(...)`，不是逐条 execute。

## 四、更新频率（内置调度器 8 个任务）

`server/app/services/scheduler.py` 的 `_build_tasks()`：

| # | 任务名 | 说明 | 周期 | 关键参数 |
|---|---|---|---|---|
| 1 | `daily_snapshot` | 每日 star 快照 | 每天 `GH_DAILY_SNAPSHOT_AT`（默认 23:50） | 落 `gh_repo_star_daily` |
| 2 | `daily_rank` | **每日刷新 周榜/月榜/总榜 三榜快照** | 每天 `GH_WEEKLY_RANK_AT`（默认 01:00） | 当前周/月 × gain/total |
| 3 | `weekly_rank` | 每周补算最近 12 周历史快照 | 每周一 `GH_WEEKLY_RANK_AT` | 12 周 gain + 周/月 total/gain |
| 4 | `collect_detail` | 补全仓库详情 | 每 86400s | limit 20，只补空字段 |
| 5 | `collect_history` | 采集 star 历史 | 60s tick 检查，距上次 >1 天 | 走官方 stargazers 接口 |
| 6 | `watch_check` | 检查关注提醒 | 每 600s | 触发 `gh_watch_event` |
| 7 | `rollup` | 回填增量指标 | 每 86400s | 重算 `star_gain_1d/7d/30d/60d` |
| 8 | `backfill` | 缺口补全 | 每 86400s | 详情/README/概要/历史 缺口 |

> **AI 中文概要已从自动调度移除**（用户 2026-10 定：禁止随意触发）——`ai_summary` / `ai_month_top`
> 不在 `tasks` 列表里，需要时经 API 手动 `llm_service.run_task`。
>
> 口径（用户 2026-10 定）：**日榜已取消**；周/月榜窗口 = 「周期首日 ~ min(周期末日, 今天)」，
> 未走完的周期截到今天（周五就是周一~周五，不空等到周日）。总榜按 `gh_repo.stars` 全库排序。

开关：`GH_SCHEDULER_ENABLED`（默认 true）。手动跑单个任务：

```bash
curl -s -XPOST localhost:9951/api/system/jobs/rollup/run     # 需管理员 Cookie
curl -s -XPOST localhost:9951/api/system/jobs/daily_rank/run # 三榜快照
```

## 五、接口清单与过滤能力（重点）

> 统一响应体 `{code, msg, data}`；`code=0` 成功。**所有非 GET 接口需管理员登录**（见鉴权章）。

### 5.1 `GET /api/repos` —— 仓库查询（过滤能力最强）

| 参数 | 类型 | 说明 |
|---|---|---|
| `q` | str | 关键词，空格分词、**词间 AND** |
| `lang` / `langs` | str | 单语言 / 多语言逗号分隔 |
| `license` | str | SPDX 协议 |
| `topic` | str | 主题标签 |
| `signal` | str | 信号标记 |
| `source` | str | 来源 |
| `min_stars` | int | star 下限（不传用默认 50；**传 0 = 关闭该条件**） |
| `max_age_days` | int | N 天内有更新（不传用默认 1095；**传 0 = 关闭**） |
| `min_gain` | int | 最小增量 |
| `major` | bool | 是否熟知名单 |
| `archived` | bool | 是否归档 |
| `has_summary` | bool | 是否已有概要 |
| `sort` | str | `stars`（默认）等，见 `repo_service.SORT_MAP` 白名单 |
| `order` | str | `desc`（默认）/ `asc` |
| `page` / `page_size` | int | 分页；**page_size 经 `utils.norm_page` 夹取，上限 5000** |
| `top_n` | int | 取前 N 条 |

### 5.2 `GET /api/ranks` —— 榜单

| 参数 | 说明 |
|---|---|
| `period_type` | `day` / `week`（默认）/ `month` |
| `metric` | `gain`（默认）/ `total` |
| `period_key` | 指定周期（如 `2026-W40`），不传取当期 |
| `q` / `langs` / `license` | 同上 |
| `min_stars` / `max_age_days` | 同上，**传 0 = 关闭门槛** |
| `exclude_major` | 过滤熟知名单 |
| `sort` / `order` | 显式排序；不传由后端按维度给默认倒序 |
| `page` / `page_size` | 默认 page_size=100 |
| `top_n` | 取前 N |

**降级链（重要，解释「为什么有些榜单是折算的」）**：

1. `metric=gain` 且区间内有**非零**每日事实 → 走事实表，`source="daily"`；
2. 否则走滚动字段 `star_gain_*`，`source="rollup"`；
3. 若 `star_gain_1d` 从未积累（日粒度缺） → 日榜退用「近 7 天日均」折算，`source="rollup_avg7"`，前端显示提示条。

### 5.3 `GET /api/history/daily` 与 `/weekly` —— 事实查询（支持多项目多天）

| 参数 | 说明 |
|---|---|
| `stat_date` | 单日，如 `2026-10-08` |
| `stat_date_from` / `stat_date_to` | **日期区间（多天）** |
| `repo_id` | 单项目 |
| `repo_ids` | **多项目**，逗号分隔 id |
| `full_names` | **多项目**，逗号分隔 `owner/a,owner/b` |
| `order` | `desc`（默认）/ `asc` |
| `limit` / `page` | **limit 默认 500，上限 5000** |

`/weekly` 参数语义相同，把 `stat_date*` 换成 `week_start` / `week_from` / `week_to`。

> 这就是你要的「多项目 + 多天 + 大 limit」：一次请求可拉 `full_names=a,b,c&stat_date_from=...&stat_date_to=...&limit=5000`。

| `GET /api/stats/dashboard` | 大屏汇总 | — |

### 5.5 返回上限总表

| 场景 | 上限 | 出处 |
|---|---|---|
| 通用分页 `page_size` | **5000** | `utils.norm_page`：`min(size, 5000)` |

## 六、中文概要：怎么拉取、怎么提炼

**存储**：`gh_repo.ai_summary`（中文）+ `summary`（原始）+ `ai_summary_tries`（尝试次数）。
**任务定义**：`gh_llm_task` 表（提示词模板可在线编辑）。
**执行**：`llm_service.run_task(task_key, model_id, limit, concurrency, group_size, allow_overwrite)`

### 6.1 硬校验（不合格直接丢弃）

`is_chinese_summary()` / `is_valid_summary()`：

- 必须**中文**，且中文字符 ≥ 20
- **不含 Markdown 小标题**（`#`、`##`）
- **≤ 900 字**
- 不含复述指令词（如「以下是」「根据提供」）

不合格 → 丢弃并累加 `ai_summary_tries`，**上限 `MAX_SUMMARY_TRIES = 3`**，超 3 次不再重试。

### 6.2 批量与并发

- **分组批量**：`group_size`（如 10~20 个仓库一个请求），而不是逐仓调用
- **并发**：`concurrency`（如 4~10）
- **只补空**：默认不覆盖已有概要；`allow_overwrite=true` 才重写

### 6.3 概要任务清单

| task_key | 选仓逻辑 |
|---|---|
| `repo_ai_summary` | 只补空，`ORDER BY stars DESC` |
| `weekly_top_summary` | **周榜前 `WEEKLY_TOP_N = 500`** 中、距上次生成 ≥ `REFRESH_COOLDOWN_DAYS = 7` 天的 |
| `month_top_summary` | 月榜前 2000 月度刷新 |
| `repo_ai_summary`（详情页） | 单仓，`ids=[repo_id]`，`allow_overwrite=true` |

### 6.4 喂给模型的素材

占位符（模板里可用）：`{full_name}` `{lang}` `{license}` `{description}` `{readme}` `{release_body}` `{latest_version}` `{period_label}`。
README 会被截断到 `max_readme_len`（任务表可配）。

## 七、「新增 star」是怎么提取的

| 口径 | 来源 | 说明 |
|---|---|---|
| `gh_repo.stars` | 官方仓库接口 | **当前总 star**，快照值 |
| `gh_repo_star_weekly.weekly_new` | ClickHouse / stargazers 历史 | **该 ISO 周新增**（WatchEvent 计数） |
| `gh_repo_star_daily.delta_stars` | 每日快照差值 | 相邻两天 star 差 |
| `star_gain_1d/7d/30d/60d` | `rollup_gains()` | 由事实表滚动求和，供榜单快速排序 |
| `gh_stat_period.gain_sum` | 周期汇总 | 周/月新增合计 |

> **口径差异**：WatchEvent 计数是「加 star 事件数」；GitHub 页面的 star 是「当前净值」（取消 star 会减）。所以历史周新增用事件计数，会比净值口径略高一点点。这是业界通用做法，可接受。

## 八、数据可靠性评估（含「为什么有的 star 数据少得可怜」）

### 8.1 结论先说

**不是拉取脚本错了，是库里的历史事实长期是空的。**

### 8.2 根因链

1. **`gh_repo_star_weekly` 原本 0 行** —— 源资料只导出了 `gh_repo` 主表 + `gh_stat_period` 周汇总，**没有逐仓周历史**。
2. 大屏柱状图 `GET /api/stats/weekly-trend` 读的正是 `gh_repo_star_weekly`；
   该表为空 → 代码**降级**去读 `gh_stat_period`（`stat_service.weekly_trend` 的 `if not rows:` 分支）。
3. `gh_stat_period` 只有 **14 周**真实 `gain_sum`（W20 + W28~W40），且 **W39 的 gain_sum = 0**。
4. 所以柱状图表现为：周数少、中间有 0、x 轴靠 `_fill_weeks()` 补 0 才连续。
5. 另有一条：默认榜单带 `min_stars≥50` 且 `3 年内有更新` 门槛，加上 `COALESCE(star_gain_7d,0) > 0` 过滤，从未采过历史的仓库会被整条滤掉。

### 8.3 已做的补救

- 新增 ClickHouse 批量补历史脚本（`server/tools/backfill_star_history.py`）。
- 幂等由 `uq_gh_star_weekly UNIQUE (repo_id, week_start)` 保证，重跑零新增。

### 8.4 清库重拉（2026-10 用户重定口径后的最终状态）

用户 2026-10 定：**清空全部 star 历史，统一从 `2026-01-01` 起重拉**，只补 star 前 5000 仓。

清库前已 dump 备份（`star_backup_<ts>.sql`，63 MB，含 `gh_repo_star_weekly` + `gh_repo_star_daily`），
随后 `DELETE` 掉周表 306,920 行、日表 52,615 行。

重拉命令与结果：

```bash
docker compose exec -T api python3 tools/backfill_star_history.py --limit 5000 --since 2026-01-01 --write
```

| 指标 | 值 |
|---|---|
| 目标仓（按 `stars` 倒序前 5000） | 5,000 |
| 命中并写入 | **4,980** |
| 周记录 | **110,432** 条 |
| 覆盖周数 | **41**（`2025-12-29` ~ `2026-10-05`） |
| 耗时 | **18 秒** |

> `2025-12-29` 那一周是 ISO 跨年周（`2026-W01`），起点落在 2025 年底，属正常。

重拉后 `POST /api/system/jobs/rollup/run` 重算滚动字段，`POST /api/system/jobs/daily_rank/run` 生成三榜快照。

### 8.5 仍存在的缺口

| 缺口 | 影响 | 补法 |
|---|---|---|
| 只覆盖前 5000 仓 | 冷门仓无历史 | 需要时加大 `--limit` 重跑（幂等） |
| `gh_repo_star_daily` 已清空 | 日粒度无数据 | 日榜已取消，不再需要；`rollup` 从周表 `days` 明细算 7d/30d/60d |
| `GH_GITHUB_TOKEN` 为空 | 官方接口 60 次/小时 | 配 token |

## 九、5 万项目能否筛选过滤拉取？

**能，但要分两种「拉取」：**

### 9.1 筛选/查询 5 万仓（读）

直接可用：

```bash
# 语言 + star 门槛 + 关键词，分页 5000/页
curl -s 'localhost:9951/api/repos?langs=Python,Go&min_stars=1000&q=llm%20agent&page=1&page_size=5000'

# 关闭所有门槛 = 全量 52736 条
curl -s 'localhost:9951/api/repos?min_stars=0&max_age_days=0&sort=stars&order=desc&page=1&page_size=5000'
```

翻页拉全量：`page_size=5000` → 约 11 页拉完 52,736 条。

### 9.2 批量采集 star 历史（写）

- **推荐**：ClickHouse 脚本，`--batch 500` 一次 500 仓，全量 52,736 仓约 106 批；
  提高 `--batch` 到 1000~2000 可减少请求数（注意 playground 查询复杂度限制）。
- **不推荐**：官方 `stargazers` 接口逐仓翻页 —— 5 万仓在匿名限速下不可行。

### 9.3 「每日新增 star 不为 0」的过滤

当前 ClickHouse 脚本**不过滤 0**（0 也是真实事实）。要只看有增长的：

```sql
-- 脚本内 SQL 可加：
HAVING count() > 0          -- 必然成立，无意义
-- 更实际的是在应用层按 weekly_new > 0 筛
```

榜单侧已有等价能力：`metric=gain` + `min_gain=1`，或走 `star_gain_7d > 0` 的滚动口径。

## 十、注意事项与坑

1. **改 Python 只需 `docker compose restart api`（≈3s）**；改 `docker-compose.yml` 的 environment 必须 `up -d api`。
2. **ClickHouse playground 是公共资源**，并发别超 ~8，批间隔给小睡；`created_at` 是 **UTC**，按周聚合要按周一取整才与项目 `_to_weeks()` 的 ISO 周口径一致。
3. **任何 OFFSET 分页的 ORDER BY 末尾都要有唯一列**，否则并发翻页会重复+遗漏（历史事故：52,615 行去重后只剩 52,594）。
4. **`gh_rank_snapshot` 有 CHECK 约束 `metric IN ('total','gain')`**，落快照前必须把 `gain_index` 归一化成 `gain`。
5. **源资料 JSONB 列是裸字面量**，PG15 会拒绝，必须经 `load_data.py` 改写。
6. **AI 概要只补空**，不要指望它自动刷新旧概要（除月榜任务和详情页手动）。
7. 大 JSON 不要经 `execute_code` 上下文（会截断），脚本里直接落 JSONL 只打印摘要。
